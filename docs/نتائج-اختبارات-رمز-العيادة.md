# نتائج اختبار تأكيد الزيارة برمز العيادة التجريبي

تاريخ التنفيذ: ٣ نوفمبر ٢٠٢٦. هذا امتداد للتطبيق الحالي، وليس استبدالًا لواجهاته أو بياناته.

## اختبارات API فعلية — ١٨ من ١٨ نجحت

شُغّل `node scripts/verify-visit-otp.mjs` ضد خادم التطبيق العامل وقاعدة PostgreSQL في التطوير. لا توجد استجابات خادم وهمية في هذه الاختبارات.

| الحالة | النتيجة الفعلية |
| --- | --- |
| محاولة بدء زيارة أو قراءة رموز العيادة دون جلسة | نجح: رفض 401 |
| جلسة مندوب يصدرها الخادم، وجلسة عيادة منفصلة، وملفات تعريف HttpOnly وSameSite | نجح؛ جلسة المندوب وحدها لا تستطيع قراءة الرموز |
| توليد رمز ستّي الأرقام وربطه بالزيارة والطبيب والمندوب وموعد خمس دقائق؛ عدم تسريبه لاستجابة المندوب | نجح؛ فُحصت البصمة والغلاف المشفّر في قاعدة البيانات |
| حفظ تقرير قبل التحقق | نجح: رفض 403 |
| رمز خاطئ | نجح: رفض 400 وخفض المحاولات إلى أربع |
| مندوب آخر يحاول تأكيد الزيارة نفسها أو استرجاعها | نجح: رفض التحقق 404، ولا تظهر له الزيارة |
| الرمز الصحيح | نجح: حالة مؤكدة، ومسح البصمة وغلاف التسليم واختفاء الرمز من المحاكي |
| إعادة استعمال الرمز الصحيح | نجح: رفض 409 |
| تبديل الطبيب أو المندوب عند الحفظ، أو إسقاط معرّف الزيارة، أو تزوير الحالة | نجح: رفض جميع الحالات |
| حفظ التقرير بعد التحقق وإعادة تحميله | نجح: 201 وحالة `Confirmed by clinic demo code`؛ محاولة حفظه مرة ثانية تُرفض 409 |
| طلبا تحقق متزامنان بالرمز الصحيح | نجح: نجاح واحد 200 ورفض الآخر 409 |
| رمز صحيح لزيارة انتهت مهلتها | نجح: رفض 410 من الخادم، ومنع التقرير وإخفاء الرمز من المحاكي |
| خمس محاولات خاطئة، ثم الرمز الصحيح | نجح: قفل عند الخامسة 429، ورفض الصحيح بعدها، وبقاء العداد عند خمس |
| ثماني محاولات خاطئة متزامنة | نجح: أربع استجابات 400 وأربع 429، دون تجاوز خمس محاولات فاشلة مسجلة |
| بدء زيارة بديلة ومحاولة استخدام مرجع الزيارة السابقة، أو تمرير هوية مندوب من المتصفح | نجح: الزيارة السابقة تُرفض 409 والهوية الإضافية تُرفض 400 |
| تعديل طبيب والبحث عنه، والمنتجات ولوحة الشركة | نجح: القيم محفوظة واللوحة تعكس التقرير الحقيقي |
| تقرير قديم غير متحقق منه | نجح: يبقى `Unverified legacy report` مع معرّف تأكيد فارغ، ولا يُعلَن كتقرير مؤكد |
| تنظيف بيانات الاختبار مع مقارنة السجلات السابقة كاملة | نجح: الأطباء والمنتجات والتقارير السابقة دون تغيير |

### كيف اختُبر انتهاء الصلاحية؟

أنشأ الاختبار زيارة ورمزًا فعليين، ثم غيّر موعد انتهاء **ذلك السجل التجريبي وحده** إلى الماضي مباشرة داخل قاعدة التطوير، وأرسل الرمز الصحيح إلى واجهة التحقق العادية. رفضه الخادم اعتمادًا على وقت قاعدة البيانات، وليس عدّاد المتصفح.

**لم يُجرَ انتظار خمس دقائق فعلية بالساعة.** لا توجد مهلة أقصر مخفية، ولا واجهة HTTP لتجاوز الانتهاء. المهلة التشغيلية تبقى خمس دقائق. التأكيد الناجح ضمن المهلة يسمح بتقرير واحد؛ انتهاء الرمز بعد نجاحه لا يلغي ذلك التأكيد.

## اختبار متصفح فعلي — مسار الشاشتين

أُجريت جولة متصفح واحدة على التطبيق العامل:

| المسار | النتيجة |
| --- | --- |
| اختيار طبيب وبدء زيارة من شاشة المندوب | نجح؛ الحفظ ممنوع قبل التأكيد، وحقل الرمز فارغ |
| فصل شاشة المندوب عن المحاكي | نجح؛ لم يخرج طلب قراءة رموز العيادة من صفحة المندوب |
| فتح المحاكي في تبويب ثانٍ وتفعيله | نجح؛ عنوان DEMO وتحذيرا عدم إثبات الحضور وعدم إرسال الرسائل ظاهران |
| إدخال رمز خاطئ | نجح؛ يظهر خطأ الخادم وتبقى أربع محاولات، ويُمسح الحقل ويبقى الحفظ ممنوعًا |
| إدخال الرمز الصحيح | نجح؛ تظهر رسالة التأكيد ويختفي رمز المحاكي بعد تحديثه |
| تغيير الطبيب ثم إعادة اختياره | نجح؛ يمنع استخدام تأكيد الطبيب الأول مع طبيب آخر |
| إعادة تحميل نموذج المندوب بعد التأكيد | نجح؛ استعادة الطبيب والزيارة المؤكدة |
| إكمال المنتج والنتيجة والملاحظات وحفظ التقرير | نجح؛ انتقال إلى سجل التقارير |
| إعادة تحميل التقرير وظهوره في ملف الطبيب ولوحة الشركة | نجح؛ الحالة الإنجليزية المطلوبة مع وصفها العربي محفوظتان |
| صفحتا المنتجات والتقارير على عرض 390×844 | نجح؛ لا تجاوز أفقي بعرض الصفحة |

اكتشف الفحص الأول تجاوزًا أفقيًا في دليل الأطباء مع اسم اختبار طويل. صُحّح بتحديد عمود الهاتف وإتاحة انكماش البطاقة، دون إعادة تصميم الدليل. أكدت صورة معاينة كاملة بعرض 390 بكسل أن البطاقات والاسم الطويل تبقى داخل عرض الصفحة؛ **لم تُجرَ جولة متصفح آلية ثانية**. لم تُرصد أخطاء JavaScript غير متوقعة؛ استجابة 400 عند الرمز الخاطئ متوقعة.

الحفظ بعد التأكيد يستخدم التحقق البرمجي الموجود للحقول؛ تمكين الزر لا يتجاوز التحقق من المنتج والنتيجة والملاحظات والتاريخ. الزيارة المؤكدة وحدها لا تنشئ تقريرًا تلقائيًا.

نجح فحص TypeScript الكامل، ثم فحص الواجهة بعد الإصلاح، ونجح بناء حزمة الواجهة بإعدادات المنفذ والمسار. حُذفت سجلات تجربة المتصفح بعد مطابقة اسمها ومعرّفاتها فقط، دون المساس بالبيانات السابقة.

## حدود النسخة

- هذه جلسات عرض تجريبية وليست حسابات مندوبين أو صلاحيات سكرتير حقيقية. صفحة المحاكي متاحة للتفعيل العام وموسومة DEMO بوضوح.
- لا يثبت الرمز الحضور الجسدي ولا هوية شخص حقيقية.
- لا واتساب أو SMS أو رسائل فعلية؛ لم تُضف أي خدمة مراسلة.
- لا يُدّعى إجراء تدقيق أمني شامل أو اختبار إنتاج أو اختبار انتظار فعلي لخمس دقائق.
- المخطط أُضيف دون حذف الجداول أو استبدال الأطباء والمنتجات الموجودة. السجلات القديمة غير متحقق منها، ولا تُمنح حالة التأكيد بأثر رجعي.

## طريقة العرض بشاشتين

1. في تبويب المندوب `/visits/new`: اختر الطبيب وابدأ زيارة معلّقة. يظهر مرجعها وعدد المحاولات والمهلة، **ولا يظهر رمز مولّد**.
2. افتح رابط المحاكي في تبويب آخر، أو `/clinic-demo` على جهاز ثانٍ لنفس التطبيق. اضغط «بدء محاكاة السكرتير»، واختر الطبيب وطابق مرجع الزيارة والمندوب.
3. انقل الرمز يدويًا إلى تبويب المندوب. جرّب رمزًا مختلفًا أولًا لرؤية الخطأ، ثم الصحيح لرؤية التأكيد.
4. أكمل المنتج والنتيجة والملاحظات والتاريخ واحفظ التقرير. تظهر الحالة الإنجليزية المطلوبة مع وصفها العربي، ويختفي الرمز من المحاكي بعد تحديثه الدوري.
5. أعد تحميل التقارير أو ملف الطبيب لترى السجل المحفوظ، وافتح لوحة الشركة لترى الإحصاءات الفعلية.

يمكن وضع التبويبين جنبًا إلى جنب. ملفا الجلسة منفصلان كي لا يحوّل فتح شاشة السكرتير جلسة المندوب إلى دور آخر.
